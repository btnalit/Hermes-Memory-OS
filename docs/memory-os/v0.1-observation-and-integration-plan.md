# Memory-OS v0.1 Observation And Integration Plan

Date: 2026-05-20

## Position

v0.1 does not start with production migration. The first v0.1 target is to keep
Memory-OS running on the `10.20.3.200` main Hermes test profile and use that
live system as the evidence source for further work.

Production migration, production Sannai migration, and real production
Hindsight export remain out of scope until a later owner-approved gate.

## Observation Track And Per-Slice Phases

v0.1 has one continuous observation track and a repeated three-phase loop for
each implementation slice.

```text
Track A: 10.20.3.200 observation, always running

Each slice:
  Phase 1: extract
  Phase 2: implement
  Phase 3: integrate
```

Track A watches whether v0 is stable under real use.

Phase 1 studies the existing `10.20.2.88` Hermes code and reference projects as
read-only sources, then turns the relevant behavior into a public module
contract. The detailed plan lives in `docs/system-modularization/`. Copied
source snapshots are private research inputs and must not be committed to this
public repo.

Sannai is explicitly not a module extraction target. Her private files and
growth mechanisms are compatibility constraints only.

Phase 2 implements the module against that contract with local tests.

Phase 3 connects the module to Memory-OS boundaries on `10.20.3.200` or local
fixtures. It can change code, prompts, and adapters needed for integration, as
long as production is untouched.

## Non-Goals

- No provider switch on `10.20.2.88`.
- No production gateway restart.
- No Sannai production migration.
- No production Hindsight bank write.
- No production identity source write.
- No Sannai private-system moduleization. Public modules only need to remain
  compatible with her profile boundary.
- No automatic Telegram or mailbox sending from inner-drive.
- No change that makes Hindsight canonical.
- No copied production source snapshot committed to GitHub.
- No production secret, session body, private prompt, token, cookie, or API key
  committed to GitHub.

## Track A: Observation On `10.20.3.200`

### Daily Evidence

Collect once per day from the main validation profile:

```bash
HERMES_HOME=/root/.hermes hermes memory
HERMES_HOME=/root/.hermes hermes memory_os status
HERMES_HOME=/root/.hermes hermes memory_os doctor
systemctl --user status hermes-memory-os-heartbeat.timer --no-pager
systemctl --user show hermes-gateway.service -p ActiveState -p MainPID --no-pager
```

Record:

- active provider
- event count
- working item count
- crystallized candidate count
- crystallized record count
- audit entry count
- index health
- prefetch mode
- latest event age
- heartbeat timer active state
- main gateway PID
- doctor findings

### Diagnostic Prompts

Run periodically through Telegram main gateway:

```text
当前记忆架构是什么？
你现在用的是什么 memory provider？
Hindsight 现在是不是 Memory-OS 的 canonical store？
上一条 Memory-OS marker 是什么？
```

Expected:

- diagnostics use current runtime facts
- `/root/.hermes/memory-os` is the canonical store
- Hindsight is optional adapter only, not canonical
- recall answers can retrieve recent Memory-OS markers without leaking private
  bodies

### Failure Criteria

Open a v0.1 bug slice if any of these happen:

- `hermes memory` no longer reports `memory_os` active
- `doctor` reports any error severity finding
- `index_health.state` remains `stale`, `missing`, or `mismatch` after a
  heartbeat
- heartbeat timer is inactive unexpectedly
- diagnostic answers reintroduce stale Hindsight-as-canonical claims
- prefetch omits current runtime facts for diagnostic prompts
- event count grows but working/candidate counts do not catch up
- raw private bodies appear in status, doctor, prefetch, or Telegram answers

### Output

Create a weekly observation report:

```text
docs/memory-os/observation-10.20.3.200-YYYY-WW.md
```

The report should include evidence snippets, not private bodies.

## Per-Slice Phase 1: Existing Hermes Subsystem Extraction

`10.20.3.200` currently has Memory-OS and the main gateway path, but it does not
have the full set of higher-level Hermes subsystems:

```text
missing on 10.20.3.200:
  Wandering Mind
  Self-Evolution Governor
  Evidence and scoring system
  mailbox
  related Speak Gate / delivery boundaries
```

v0.1 therefore includes modularizing these existing systems from the
`10.20.2.88` codebase before integrating them into the blank/test Hermes
environment.

### Source Snapshot Rule

Allowed:

- copy relevant `10.20.2.88` source code and non-secret config for local study
- use read-only SSH/rsync/scp operations
- keep copied source under a private, git-ignored research path
- write a public module map that describes architecture, interfaces, and
  boundaries without private bodies or secrets

Not allowed:

- no modification on `10.20.2.88`
- no restart on `10.20.2.88`
- no production config write
- no raw sessions, private prompts, tokens, cookies, or API keys in this repo
- no direct copy-paste of environment-specific paths into reusable module APIs

Recommended private snapshot root:

```text
D:\Hermes agent manager\private\hermes-10.20.2.88-snapshot\YYYYMMDD-HHMMSS\
```

Recommended public outputs:

```text
docs/memory-os/v0.1-module-map.md
docs/system-modularization/
```

Additional reference source:

```text
/vol1/1000/hermes-self-evolution/
```

This older Self-Evolution modularization project can inform installer shape,
demo fixtures, bridge-plugin design, and governance pipeline boundaries. It is
not the full target architecture.

### Module Map

The module map should classify existing Hermes subsystems by layer:

| Existing subsystem | Target layer | v0.1 goal |
| --- | --- | --- |
| Wandering Mind | L2 Cognition / L4 Expression output | Port as a bounded Memory-OS read-view module that can output `[SILENT]` or event/candidate text. |
| Self-Evolution Governor | L2 Cognition / governance | Port policy/evolution checks as read-only scoring and candidate generation, not direct self-modification. |
| Evidence and scoring system | L2 Cognition | Port scoring as explainable evidence records attached to events, working items, and candidates. |
| InnerDriveEngine | L2 Cognition | Run Lingering / Emotional / Curiosity / Attention on real Memory-OS events. |
| mailbox | L0/L4 Infrastructure/Expression adapter | Port as an adapter boundary; v0.1 test mode must not send unless explicitly enabled. |
| Speak Gate / delivery rules | L4 Expression | Keep outward delivery separate from cognition; default test mode is no-send. |

Sannai-specific heartbeat, diary, identity, and curation systems stay out of
the public module inventory.

### Module Contract

All ported modules should depend on Memory-OS through narrow interfaces:

```text
MemoryOSReadView
  read recent event summaries
  read working summaries
  read approved crystallized summaries
  read identity manifest metadata
  read relationship summaries

MemoryOSWriteSink
  append event
  update working memory
  create crystallized candidate
  append audit

DeliverySink
  disabled by default in v0.1
  records would-send audit only unless explicitly enabled
```

The goal is that a blank Hermes host can install Memory-OS plus these modules
without inheriting hidden production assumptions.

The current read-only production audit found that this work is necessary:
Memory-OS is already portable, while Wandering Mind, Self-Evolution Governor,
Ops-Gate, evidence/scoring, household digest, mailbox, and Speak Gate are still
split across cron jobs, skill scripts, bridge plugins, and profile-local state.
See `docs/system-modularization/02-existing-system-audit.md`.

## Per-Slice Phase 3: System Integration

Integration is allowed during the observation period. It should stay local or
on `10.20.3.200` and use clear read/write boundaries.

### B1: L2 Inner Drive Runtime Integration

Layer: L2 Cognition.

Goal: make the existing Inner Drive surfaces useful on real Memory-OS events.
This is the first v0.1 cognition-layer runtime integration. It can be deployed
directly on the `10.20.3.200` test environment after the module map confirms
its dependencies, because it writes only Memory-OS controlled state and has no
production side effects.

Components:

```text
InnerDriveEngine
├── Lingering Manager
├── Emotional Manager
├── Curiosity Manager
└── Attention Updater

Adjacent L2 systems:
├── Wandering Mind
├── Self-Evolution Governor
└── Evidence and scoring system
```

Allowed:

- tune Lingering / Emotional / Curiosity / Attention classification
- improve decay and trace output
- add status views for working memory evolution
- run heartbeat on the test profile
- read Memory-OS events and write working memory, crystallized candidates,
  audit entries, and module-local state
- deploy the runtime integration to `10.20.3.200` main test profile
- collect live evolution evidence from real test events

Not allowed:

- no autonomous Telegram send
- no mailbox send
- no identity write
- no production config write
- no direct approved crystallized write without owner approval
- no write to `10.20.2.88`

Acceptance:

- real `10.20.3.200` events produce explainable working state
- `trace` can show why a lingering/emotional/curiosity item exists
- repeated heartbeat is idempotent
- no outward messages are sent
- `memory_os doctor` stays ok after the integration is enabled
- working/candidates/audit/module-local state are the only write surfaces

### B2: Wandering Mind Read-View Alignment

Goal: align Wandering Mind with Memory-OS as a bounded read source without
taskifying the right-brain contract. Since `10.20.3.200` does not currently
have Wandering Mind, v0.1 must first port it as a reusable module from the
`10.20.2.88` code snapshot.

Allowed:

- add a Memory-OS bounded read view for Wandering Mind
- read recent event summaries, working summaries, approved crystallized memory,
  identity manifest metadata, and relationship summaries
- write wandering output as event or candidate on test profile

Not allowed:

- no proposal write
- no agenda write
- no forced output when `[SILENT]` is appropriate
- no production Sannai or main gateway change

Acceptance:

- Wandering Mind can run against a test Memory-OS root
- output remains free-form or `[SILENT]`
- all writes are event/candidate only unless explicitly approved

### B3: Speak Gate / Foreground Context Integration

Goal: keep foreground conversations grounded in the correct Memory-OS views.

Allowed:

- refine diagnostic grounding
- refine bounded prefetch section ordering
- add prompt-facing context labels that reduce stale-memory confusion
- add tests from observed Telegram failures

Not allowed:

- no global system prompt patch as a substitute for provider behavior
- no Sannai personality-breaking diagnostic mode by default

Acceptance:

- diagnostic questions use runtime facts
- ordinary recall questions use indexed recall
- Sannai-style ordinary self-memory prompts do not turn into system reports

### B4: Operator Observability

Goal: make live debugging easy without reading private bodies.

Allowed:

- improve `status`, `doctor`, `inspect`, `trace`, and `diff`
- add observation report generators
- add stale/stuck heartbeat detection
- add index/working/candidate trend summaries

Not allowed:

- no raw prompt/session body output by default
- no secret output
- no destructive cleanup by default

Acceptance:

- an operator can tell whether Memory-OS is healthy from one report
- private text remains redacted by default
- failures point to the next safe action

## Defer Until Later

These are not v0.1 default tasks:

- production provider migration
- production Sannai migration
- real production Hindsight adapter export
- write-side stale-memory adjudication
- vector retrieval
- graph retrieval
- automated production restart wrapper

They can be reconsidered only after observation produces a concrete need and a
separate gate is written.
